# Architecture Plan: Automation Miner v2 — Storage & Indexing at Scale

## The Problem
250 topics × 7 opportunities = **1,750+ AM briefs**. Current flat file structure with 42 files works fine now but will become a nightmare at 1,750. Discovery, cross-referencing, filtering, and maintenance all break.

## Design Principles
1. **Zero change to the Miner engine itself** — the skill, its phases, ICE scoring, strategic filters all stay untouched
2. **The output pipeline changes** — how results are stored, indexed, and queried
3. **Scale to thousands** without manual maintenance
4. **Backward compatible** — existing 42 AM briefs remain valid

## Proposed Architecture

### Current (v1)
```
obsidian/automation-mining/
├── _index.md              ← One big flat table growing linearly
├── AM-001-<slug>.md       ← All flat in one directory
├── ...42 more files...
└── runs/                  ← One run log per domain
    └── YYYY-MM-DD_<slug>.md
```

### Proposed (v2)
```
obsidian/automation-mining/
├── _index.md                    ← Project overview + registry stats (NOT the full table)
├── registry.json                ← Machine-readable master index (compact JSON, auto-generated)
├── runs/                        ← One run log per domain
│   ├── YYYY-MM-DD_<slug>.md
│   └── ...
└── opps/                        ← Partitioned by domain run
    ├── german-healthcare/
    │   ├── AM-001-<slug>.md
    │   ├── AM-002-<slug>.md
    │   └── ...7 opps
    ├── real-estate-smart-building/
    │   ├── AM-008-<slug>.md
    │   └── ...7 opps
    ├── carrier-bidding-eshop/
    ├── precision-irrigation/
    ├── greenhouse-climate/
    ├── wine-cellar-inventory/
    └── ...future domains (up to 250)
```

### Why Partitioning Helped Over Flat
- `ls opps/german-healthcare/` = immediately shows all 7 opps for that domain
- Adding a new domain = create one subdirectory, no file rename conflicts
- Scoping agent queries: "find all monitoring-layer opps in agriculture" = scan opps across specific domains
- Human navigation: open the domain folder, not a 42-entry flat list

Changes from current registry format:

- Cross-indices (`by_layer`, `by_ice_range`, `by_status`) for fast agent queries
- Runs list for timeline navigation

### Changes Required

1. **New directory structure** — move existing AM-XXX files into domain subdirectories
2. **Update workspace-indexer.py** — handle partitioned AM structure (or build dedicated `miner-reindex.py`)
3. **Create registry.json** — parallel to _index.md for machine consumption
4. **Update _index.md** — strip the 42-entry flat table, keep overview + pipeline metrics + link to registry
5. **Update Automation Miner skill** — output protocol section: write to `opps/<domain-slug>/` instead of flat directory
6. **Update HEARTBEAT.md** — add miner reindex to daily checklist
7. **Migrate existing 42 opps** — move to partitioned structure
8. **Validate** — workspace-indexer still works, registry queries produce correct results

### Migration Path (Existing 42 opps)

The current flat files have internal links and YAML frontmatter. Migration is safe:
- Rename `AM-XXX-<slug>.md` → `opps/<domain-slug>/AM-XXX-<slug>.md`
- Add `domain:` field to YAML frontmatter (some already have it)
- Update `_index.md` tables
- Reindex

### Agent Query Protocol (How to Find Things)

With 1,750 opps, agents need fast discovery:
```
"Find monitoring automations in agriculture"
→ Read registry.json → by_layer.monitoring → intersect with agriculture domains
→ Returns: AM-006, AM-012, AM-013, AM-019, AM-024, AM-026, AM-034, AM-039
→ Read those specific opp briefs

"Show me all vision-grade opps"
→ Read registry.json → by_ice_range.vision_80plus
→ Returns: AM-015, AM-022, AM-029, AM-036, AM-038
```

### What Stays the Same
- The Miner engine phases, scoring, filters — untouched
- AM-XXX numbering — sequential, global
- Full opportunity brief format — unchanged
- Each AM-XXX file is still self-contained, readable standalone
